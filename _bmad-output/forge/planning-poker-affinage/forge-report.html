Planning poker pour ateliers d'affinage

Idée forgée par Eric, scrum master. Objectif : clarifier avant de formaliser.

Issue : idée durcie. Le déroulé, les rôles et le périmètre V1 sont tranchés ; il reste un point ouvert.

Le cycle d'un ticket

Vote caché→Révélation nominative→Discussion des écarts→Revote (tours précédents visibles)→Validation par l'animateur→Ticket suivant

Décisions verrouillées

  • Deux rôles. L'animateur crée la session et pilote tout ; il vote ou non ; son rôle est transmissible. Les votants rejoignent par lien + pseudo unique.
  • Vote. Carte modifiable jusqu'à la révélation ; un arrivant peut voter sur le ticket en cours ; chacun voit qui a déjà voté, sans la valeur.
  • Cartes fixes : 0 1 2 3 5 8 13 21 ? ☕
  • Valeur finale choisie explicitement par l'animateur, ou ticket marqué « non estimé ».
  • Tickets saisis à la main (liste collée, ajout à la volée) ; export récapitulatif copiable / CSV.
  • Session éphémère mais robuste : survit aux rafraîchissements, expire après ~24h.
  • Accès en ligne par lien long non devinable, sans mot de passe.

Écarté de la V1

  • Intégration Jira : authentification, API et mapping trop coûteux ; la recopie manuelle est acceptée.
  • Comptes et historique : inutiles pour des sessions éphémères ; l'export sert d'archive.
  • Jeu de cartes configurable, ½ / 40 / 100.

Points faibles qui ont survécu

  • Si l'animateur est déconnecté, il ne peut pas transmettre son rôle lui-même : mécanisme à définir.
  • Qui possède le lien entre dans la session ; les titres de tickets sont exposés (risque accepté).
  • Hypothèse d'usage : visio / hybride, 3 à 12 personnes, une session à la fois.
