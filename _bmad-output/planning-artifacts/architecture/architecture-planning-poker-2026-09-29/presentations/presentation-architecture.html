Planning Poker · Architecture V1
Le produit

Un planning poker qui appartient à l'équipe

Il remplace Scrum Poker Online pendant nos ateliers d'affinage, à distance ou en hybride.

  • Voter à l'aveugle, révéler, discuter, effacer, recommencer.
  • Aucun rôle privilégié : n'importe qui crée, révèle, masque ou efface.
  • Accès par simple lien, sans compte, sur PC ou téléphone.
  • Une coupure réseau ne fait jamais perdre sa place ni son vote.
  • Seul un plantage ou un redémarrage du serveur peut perdre une session : risque accepté.
Conséquence pour l'architecture : le serveur fait autorité sur l'état de la session ; le navigateur n'en est qu'un reflet.

Les grands choix

Quatre choix structurants, et leur raison

WebserviceJava 25 LTS et Spring Boot 4.1.1

LTS en vigueur. Spring est le framework le plus répandu et le mieux documenté : le plus fiable pour du code écrit par des agents. Build Maven 3.9.16.

Écartés : Quarkus (plus léger) et Micronaut. Attention : Spring Boot 4.1.1 va jusqu'à Java 26, pas 27.

FrontAngular 22

Choix de l'équipe. Zoneless, OnPush et signals par défaut, tests Vitest. Un seul SessionService détient la connexion et l'état (AD-10).

Écartée : une bibliothèque cliente WebSocket ; l'API native suffit.

DépôtUn monodépôt

contract/, backend/, frontend/, deploy/ dans un seul dépôt Git : un message change des deux côtés dans le même changement.

Évite : la dérive du contrat de messages entre front et webservice.

ÉchangesREST pour entrer, WebSocket pour la séance

REST crée, vérifie et rejoint. Ensuite, toutes les actions de séance passent par un seul WebSocket, dans un seul ordre.

Écarté : STOMP et SockJS. On garde un WebSocket brut, avec des messages JSON définis par le contrat.

Communication hybride

Entrer par REST, vivre la séance en WebSocket

Entrer : quatre endpoints REST, pas un de plus

  • GET /api/health : sonde de réveil
  • POST /api/sessions : crée et fait entrer le créateur
  • GET /api/sessions/{id} : 204 ou 404
  • POST …/{id}/participants : rejoindre, ou reprendre un pseudo

Ils renvoient participantId et le secret participantToken.

La séance : un seul WebSocket brut

  • WS /ws/sessions/{id} est le seul canal des actions de séance.
  • Surface fermée : toute nouveauté commence par le contrat.
Pourquoi : un seul canal donne un seul ordre des actions. Deux actions quasi simultanées aboutissent au même état final chez tous (FR-17).

Déploiement V1

Deux services sur Render Free, pour zéro euro

Deux origines

Le front lit l'URL de l'API dans /config.json, généré depuis API_BASE_URL. L'API n'accepte que ALLOWED_ORIGINS. CSP stricte, HTTPS et WSS seulement.

Pas de veille en séance

Render s'endort après 15 min sans message entrant. Le heartbeat du client, toutes les 5 s, le garde éveillé tant qu'une séance a lieu (NFR-1b).

Un filet de sécurité

Test de charge (13 participants, 65 connexions) dès la première story WebSocket. En cas d'échec : repli sur Northflank, puis Oracle Always Free avec k3s.

Webservice hexagonal

Les règles au centre, les protocoles autour

  • domain : Java pur. Règles du jeu, synthèse (moyenne, plus votée, min, max, consensus), instantané filtré.
  • application : cas d'usage, balayeur des délais, ports SessionStore et SessionBroadcaster, Clock.
  • adaptateurs : traduisent REST, WebSocket ou stockage. Ils ne prennent jamais de décision métier.
  • config : assemblage Spring, CORS, origines WebSocket.

Garde-fou automatique

Un test ArchUnit fait échouer le build si domain importe Spring, Jackson ou jakarta, ou si le sens des dépendances est violé.

Bénéfice : PostgreSQL ou Jira arriveront comme de nouveaux adaptateurs, sans toucher aux règles (NFR-9).

Le cycle d'une action

Une intention, un verrou, une version, un instantané

Actions simultanées

Sérialisées par session : la dernière reçue s'applique, et tous voient le même état final.

Intention nommée

reveal, jamais « inverser ». Un clic tardif ne peut pas effacer le tour suivant.

Déjà satisfaite

reveal sur un tour révélé ne change rien : ni version, ni erreur.

Connexion lente

File d'envoi bornée (2 s, 64 Ko). Au-delà, la connexion est fermée et le client se reconnecte.

Vote à l'aveugle

Pourquoi personne ne peut tricher

Exemple : tour caché, Sofia a joué 5 et Karim 8. Chacun reçoit son instantané.

Instantané envoyé à Sofia

round: { status: HIDDEN }
{ pseudo: "Sofia", hasVoted: true, vote: "5" }
{ pseudo: "Karim", hasVoted: true, vote: null }

Instantané envoyé à Karim

round: { status: HIDDEN }
{ pseudo: "Sofia", hasVoted: true, vote: null }
{ pseudo: "Karim", hasVoted: true, vote: "8" }

Extrait simplifié du squelette normatif sessionState.

  • La carte des autres n'arrive jamais dans mon navigateur. Le domaine filtre l'instantané par destinataire : ni les outils de développement ni le trafic réseau ne la montrent.
  • Le serveur décide. Le client n'envoie que des intentions ; règles et synthèse sont calculées par le domaine.
  • Pas de vote après coup. Voter sur un tour révélé renvoie ROUND_REVEALED ; un observateur reçoit NOT_A_VOTER.
  • Personne ne parle à ma place. Mon participantToken est secret : jamais dans une URL, un instantané ou un journal.
  • Rien ne fuit dans les journaux : ni jeton, ni vote d'un tour caché, ni pseudo.

Risque accepté (confiance d'équipe) : reprendre le pseudo d'un participant déconnecté n'est pas bloqué (FR-8, NFR-6).

Le contrat d'abord

contract/ est la source de vérité

  • La première story du build livre le contrat complet, avec un exemple de chaque message, avant toute story front ou webservice.
  • Types Java et TypeScript écrits à la main ; des tests valident les exemples contre les JSON Schema, des deux côtés.
  • Un message change dans le même changement que le code des deux côtés.
  • Aucun champ ne circule s'il n'est pas décrit.
  • Entre deux versions : ajouts seulement, ni suppression ni renommage (AD-13).

Pourquoi : des agents qui codent en parallèle ne doivent pas inventer chacun leur version d'un message.

Identité

Trois identifiants, un seul secret

IdentifiantNatureOù il circule
sessionId128 bits aléatoiresdans le lien de session
participantIdUUID publicdésigne un participant dans l'état
participantToken128 bits, secretjamais dans une URL, un instantané ou un journal

Tous générés avec SecureRandom. Le jeton est rangé dans le localStorage (pp.token.{sessionId}), partagé par les onglets : plusieurs onglets = un seul participant.

Reprise depuis un autre appareil (FR-8) : nouveau jeton émis, l'ancien est révoqué et ses connexions fermées en 4401.

Poignée de main hello

  1. Le client ouvre /ws/sessions/{sessionId}.
  2. Premier message, sous 5 s : hello {participantToken}.
  3. Session inconnue ou expirée : fermeture 4404 → « Session introuvable ».
  4. Puis le jeton :
    actifparticipant reconnecté
    retiré, pseudo libreremis à sa place
    inconnu, révoqué, pseudo pris4401 → écran Rejoindre, pseudo prérempli
  5. Le serveur envoie l'instantané sessionState.

Présence et reconnexion

L'inactivité ne déconnecte jamais

Seul l'état réseau compte. Écouter sans rien toucher, onglet en arrière-plan ou téléphone verrouillé : on reste dans la session.

SignalQui, quandÀ quoi il sert
ping de protocoleserveur, 5 svivacité : le navigateur répond seul, même onglet caché
tickserveur, 5 sle client détecte la perte (12 s sans message)
heartbeatclient, 5 sgarder Render éveillé, uniquement

Reconnexion du client

Immédiate, puis après 1, 2, 4 et 8 s, puis toutes les 10 s. Aussi immédiate sur online et au retour au premier plan. Le balayeur serveur passe chaque seconde.

Deferred

Ce qui est volontairement reporté

Adaptateur PostgreSQL

Derrière SessionStore, quand un besoin de persistance apparaîtra. Aucun en V1.

Plusieurs instances

Exigent un stockage partagé et une diffusion entre instances. Nouvel AD, qui remplacera la règle « une seule instance ».

OpenShift et GitLab CI

Manifests et pipeline écrits au passage en entreprise. Images déjà prêtes, config.json en ConfigMap.

Intégration Jira

Un nouvel adaptateur sortant, en V2 ou V3, si l'outil est adopté.

Observabilité

Métriques et traces plus tard : les journaux JSON suffisent en V1.

Hébergeur de repli

Northflank, puis Oracle Always Free avec k3s, si le test de charge ou l'usage réel échoue sur Render.

Bibliothèque cliente WebSocket côté Angular : l'API native suffit. Si une bibliothèque arrive un jour, elle reste confinée à SessionService.
